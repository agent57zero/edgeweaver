    Atlas: operations scripts

    TLDR

    Operations code keeps dark machinery bounded: budgets can suppress optional work, writes can survive a brain outage, channels recognize only pinned authority, flags start disabled, and recovery and security checks expose failure. These scripts explain mechanism without publishing schedules, network coordinates, account topology, custody, or secret values. Built and verified does not mean armed or live.

    What this page covers

    The entries cover resource limits, degraded memory, configuration initialization, channel scoping, security review, and disaster-recovery rehearsal. The shared pattern is fail closed: missing authority, credentials, or explicit arming must not turn into permissive behavior. Some checks are deliberately best-effort until the real host and accounts exist, and the repository-only recovery drill is only one leg of the full human-governed recovery runbook.

    File entries

    scripts/budget/budget.mjs active-code

    What it is. The pure resource-meter policy for model spend, optional loops, proactive attention, and voice usage.
    What it contains. It records estimated spend and voice minutes, compares spend with a human-set monthly ceiling, emits normal, warning, or degraded states, and suppresses optional work only at the hard limit. An unset ceiling stays visibly unset because gate G6 is pending.
    Who reads it and when. Waking, voice, and scheduled loop callers consult it before optional actions. Operators set policy outside this file; tests use invented numbers.
    How to verify or reproduce it. Exercise unset, below-warning, warning, and cap states, plus accumulated voice minutes. Confirm the code never invents a ceiling and mandatory safety work remains distinguishable from optional work.
    Related concepts. See budgets and attention, proactive senses, and voice cost.

    scripts/dr/dr-drill.mjs active-code

    What it is. A repository-machinery disaster-recovery rehearsal that clones the current project into a disposable workspace and runs its complete verify suite.
    What it contains. It creates scratch space, performs a local clone, guards against recursive self-invocation, measures recovery time, reports whether the suite reached all-pass, and removes the scratch tree afterward. It contains no secret, brain, or soul restoration.
    Who reads it and when. An operator runs it as one evidence leg of the broader recovery runbook. The verify suite may invoke it with a recursion guard.
    How to verify or reproduce it. Run from a clean committed state, confirm the clone verifies independently and the scratch location is removed. Treat success as proof of buildable machinery only, not full continuity recovery.
    Related concepts. See backups and recovery, failure drills, and its verifier.

    scripts/init-flags.mjs active-code

    What it is. The non-destructive initializer for live operational flags from the committed disabled defaults.
    What it contains. It creates the ignored state document when absent, adds newly introduced component, task, and channel keys as disabled, preserves every existing entry verbatim, and refuses to overwrite malformed state. It never enables a component.
    Who reads it and when. Operators run it after clone, schema change, or recovery. Other code reads the resulting state only after its own gate checks.
    How to verify or reproduce it. Start with absent, partial, armed, and malformed fixtures. Confirm missing keys are added, existing values survive, every default is disabled, and malformed state fails without replacement.
    Related concepts. See dark-by-default machinery, arming, and gates.

    scripts/seal-secrets.cmd described-not-shown

    What it is. An Alan-present interactive helper for sealing the disaster-recovery secret bundle.
    What it contains. It guides human key handling, encrypts a prepared bundle, verifies decryption before removing plaintext staging, and places sealed copies under governed custody. Coordinates and topology are withheld.
    Who reads it and when. The human custodian runs it during recovery; runtime agents do not.
    How to verify or reproduce it. Complete the private seal-and-open rehearsal and confirm no plaintext residue. Never paste keys, locations, or account details into evidence.
    Related concepts. See secret recovery, human custody, and credential walls.

    scripts/security/security-audit.mjs active-code

    What it is. The quarterly security-floor checklist runner for repository secrets, runtime extensions, network exposure, pinned senders, and credential separation.
    What it contains. It scans tracked text for key-shaped material, checks local channel state when present, and tests whether the active gh credential context can reach the private gate authority. That check does not establish that the active gh credential is the runtime credential. The extension and listening-service legs are best-effort declarations in the dark build and require real host review at arming.
    Who reads it and when. Operators run it during the security cadence and before arming. The dedicated verifier asserts that each named leg reports a result.
    How to verify or reproduce it. Inspect each result independently rather than trusting only the aggregate. Re-run host, account, and network checks in the real environment, including the actual runtime-credential separation test, and report failures without printing sensitive values or coordinates.
    Related concepts. See security cadence, credential separation, and the gate boundary.

    scripts/telegram/channel-policy.mjs active-code

    What it is. The pure sender-classification wall for the planned parent messaging channel.
    What it contains. It recognizes Alan only through a pinned entry, assigns the governed audience, permits lesson confirmation only for that pinned confirmer, and sends every other known or unknown sender to the same brief deferral path. Unknown senders default to untrusted; known non-parent entries retain their configured untrusted status. Tier-changing decisions still require a separate out-of-band check by the caller.
    Who reads it and when. Channel adapters call it for every inbound sender after pairing. Verifiers use invented identifiers; the live channel remains dark.
    How to verify or reproduce it. Test pinned confirmer, known non-parent, unknown sender, missing state, and lesson-confirm paths. Confirm no message content can promote its own sender authority.
    Related concepts. See the gated body, audience scopes, and confirmation authority.

    scripts/telegram/init-interlocutors.mjs described-not-shown

    What it is. The ignored-state initializer for the planned messaging interlocutor map.
    What it contains. It reads only the allowed environment-variable name, writes a parent entry when privately configured, otherwise writes a clearly marked pending shape, and keeps unknown senders public and untrusted.
    Who reads it and when. An operator runs it during pairing; policy reads it. It never enables the channel.
    How to verify or reproduce it. Parse the generated shape, confirm the untrusted default and confirmer flag, and keep all real identifiers out of logs and documentation.
    Related concepts. See pairing, audience, and dark configuration.

    scripts/wal/wal.mjs active-code

    What it is. The append-first write-ahead buffer for degraded brain availability. It preserves intended writes while telling callers that recall is provisional rather than guessing.
    What it contains. It fingerprints content, appends timestamped kind and payload records to ignored daily JSONL, replays files through an injected sink, suppresses repeated fingerprints seen during that replay, and moves drained files into a replayed area. A health helper converts failed reachability into an explicit degraded result. Brain-side content fingerprinting provides the complementary cross-run deduplication layer. The module is constructed and dark-verified, but production callers are not yet all armed through it.
    Who reads it and when. Write paths call it before a remote brain write once the body arms. Operators inspect backlog and replay status; verifiers use an isolated state directory.
    How to verify or reproduce it. Simulate outage, duplicate appends, successful replay, failed and healthy pings, and cleanup. Confirm ordering, counts, archived drained files, identical fingerprints for identical content, and no claim that unavailable recall succeeded.
    Related concepts. See memory degradation, outage behavior, and the WAL verifier.
