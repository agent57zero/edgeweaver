    Atlas: edge functions

    TLDR

    Edge functions are the guarded doors around remote memory. One interface serves general Open Brain capture and search, another governs reusable agent lessons, recall-scoped applies Edgeweaver's provenance and audience walls, embed-backfill repairs missing vectors, and sql-migrate is a powerful operator-only schema tool. Reviewed mirrors live beside deployment sources so code can be audited without publishing service coordinates or credentials.

    What this page covers

    The deployable functions live under the Supabase source tree. Three smaller files under the scripts tree are byte-matched review mirrors of deployed functions at this snapshot; recall mirror equality is also pinned by verification. Dependency manifests make larger functions reproducible. A shared access-key name is not the whole policy: each entry explains whether the door is general operator tooling, governed agent memory, or the narrower consumer-scoped recall path.

    File entries

    scripts/edge-functions/embed-backfill.ts archive

    What it is. The reviewed repository mirror of the deployed missing-embedding backfill function.
    What it contains. It matches the deployable source byte for byte at this snapshot: select rows without vectors, request embeddings in batches, update rows, and report remaining work. Coordinates and keys stay outside Git.
    Who reads it and when. Reviewers inspect it with ingestion changes; deployment uses the Supabase-tree copy.
    How to verify or reproduce it. Compare bytes with the deployable file and run the private batch to zero remaining rows, checking errors without exposing content.
    Related concepts. See semantic memory and the deployed source.

    scripts/edge-functions/recall-scoped.ts archive

    What it is. The reviewed mirror of the deployable Edgeweaver recall-scoping wall.
    What it contains. It carries the same embedding, semantic match, audience, provenance, and fail-closed filtering logic as the deployed copy. It stores no credential values.
    Who reads it and when. Memory reviewers use it beside conventions; runtime deployment uses the Supabase-tree copy.
    How to verify or reproduce it. The recall-scoping verify requires byte equality and exercises unlabeled, pre-birth, audience, library, fiction, interpretation, and experienced fixtures.
    Related concepts. See recall policy and the deployed wrapper.

    scripts/edge-functions/sql-migrate.ts archive

    What it is. The reviewed mirror of the guarded schema-migration edge function.
    What it contains. It accepts an authenticated SQL script, executes it as one operator transaction context, returns bounded status, and closes its database client. It is powerful operator tooling, not ordinary runtime behavior.
    Who reads it and when. Schema reviewers inspect it before a governed migration; deployment uses the matching Supabase-tree copy.
    How to verify or reproduce it. Compare it bytewise with the deployable source and test only against an approved disposable schema before any live migration.
    Related concepts. See change authority and the deployed source.

    supabase/functions/agent-memory-api/deno.json schema-data

    What it is. The import map that pins the agent-memory function's runtime libraries.
    What it contains. It maps validation, HTTP routing, and database-client package names to explicit versions, making deployment resolution reviewable.
    Who reads it and when. The edge runtime and maintainers read it whenever the agent-memory API builds.
    How to verify or reproduce it. Reproduce dependency resolution in the supported runtime and review every version change with the function tests and upstream licenses.
    Related concepts. See governed lessons and the API source.

    supabase/functions/agent-memory-api/index.ts active-code

    What it is. The governed API for reusable agent memories: recall, writeback, usage traces, review, and audit around the sidecar lesson store. It is distinct from ordinary thought capture.
    What it contains. It validates versioned request bodies, scope, runtime, channel, memory payload, review action, and usage reports. Recall embeds a query, filters and ranks eligible rows, returns policy flags, and records a trace. Writeback derives one or more memory rows, detects only bounded unsafe shapes through unsafeReasons, such as key-like strings, large code blocks, and raw-transcript-like input; it does not establish general instruction safety. It fingerprints records and defaults agent-written lessons to evidence with confirmation pending rather than instruction authority. Review routes can confirm, restrict, reject, stale, or edit records while updating audit history. Access is guarded by the configured brain key; credentials and service coordinates are environment-only.
    Who reads it and when. Approved agent-memory clients call it during recall and post-task writeback. Alan or an authorized review surface handles pending lessons; operators inspect audits during incidents.
    How to verify or reproduce it. Exercise schema rejection, authentication, scoped recall, trust-default writeback, duplicate fingerprints, bounded unsafe-shape refusal, usage marking, every review transition, and audit events against a disposable database. Confirm no pending lesson becomes instruction-grade without review.
    Related concepts. See lessons and trust defaults, confirmation, and scope.

    supabase/functions/embed-backfill/index.ts active-code

    What it is. The deployed batch worker that gives semantic vectors to thought rows inserted without embeddings.
    What it contains. It selects a bounded batch of missing rows, sends truncated content to the configured embedding service, patches successful vectors in small parallel groups, counts remaining work, and returns bounded error summaries. Privileged database and vendor credentials come only from the edge environment.
    Who reads it and when. An operator invokes it after bulk or direct ingestion until the missing count reaches zero. Normal recall benefits from the result but does not call this maintenance function.
    How to verify or reproduce it. Run on a small approved batch, compare embedded and remaining counts, inspect errors privately, repeat to zero, and confirm already embedded rows are never selected.
    Related concepts. See semantic recall, library ingestion, and the review mirror.

    supabase/functions/open-brain-mcp/deno.json schema-data

    What it is. The import map for the Open Brain MCP edge function.
    What it contains. It pins the MCP transport, protocol SDK, HTTP framework, validation library, and database client to explicit versions.
    Who reads it and when. The edge runtime resolves it at build and deployment; maintainers review dependency updates.
    How to verify or reproduce it. Resolve in the supported runtime, run the function's integration checks, and inspect upstream license and security changes before updating pins.
    Related concepts. See Open Brain and the MCP source.

    supabase/functions/open-brain-mcp/index.ts active-code

    What it is. The general Open Brain MCP server for external clients to capture, search, fetch, list, and summarize thoughts. It is not the narrower Edgeweaver consumer-recall wall.
    What it contains. It builds an authenticated MCP server over streamable HTTP, generates embeddings, extracts metadata for capture, and registers read and write tools with protocol annotations. Search and fetch produce citation-shaped results; list and statistics expose bounded summaries; capture writes a thought with generated embedding and structured metadata. A configurable citation base affects links, while database, embedding, and access credentials remain in the edge environment. Because these tools serve broader owner workflows, their general search behavior must not be mistaken for the provenance and audience policy applied to a being's episodic or study recall.
    Who reads it and when. Alan and approved external AI clients use the MCP interface for Open Brain workflows. Edgeweaver runtime consumers should call the scoped wrapper appropriate to their role.
    How to verify or reproduce it. Test authentication, every tool schema, embedding and metadata failures, bounded result shapes, citation construction, read-only annotations, and capture persistence in a disposable project. Separately prove the runtime cannot bypass recall-scoped through credential assignment.
    Related concepts. See brain interfaces, credential separation, and scoped recall.

    supabase/functions/recall-scoped/index.ts active-code

    What it is. The deployable enforcement point that turns semantic memory search into consumer-safe recall by applying both provenance class and audience scope before results leave the brain.
    What it contains. It authenticates the caller, requires a query, accepts a consumer value, obtains a query embedding, overfetches semantic candidates, loads their source and metadata, derives experienced, interpretation, fiction, or library class, and applies the consumer allowlist plus audience algebra. Only the literal consumer value study receives the study policy; every other value currently falls through to the episodic policy. Unlabeled rows fail closed; governed pre-birth rows default to the parent scope rather than public. Results retain useful provenance and similarity while content is bounded.
    Who reads it and when. Waking, voice, study, and other being-facing recall clients call it with an explicit audience scope. Operators review its policy with memory conventions before deployment.
    How to verify or reproduce it. Run the offline scoping verifier across every class and scope, require mirror equality, test authentication and upstream failures in a disposable deployment, and confirm no raw candidate is returned before both filters pass.
    Related concepts. See the one recall door, audience algebra, and the review mirror.

    supabase/functions/sql-migrate/index.ts active-code

    What it is. The deployable guarded DDL runner for reviewed multi-statement schema migrations.
    What it contains. It requires the configured brain access key, validates that the request contains SQL text, opens one direct database client with prepared statements disabled for script execution, runs the supplied text, returns a bounded statement or error result, and always closes the client. It contains no migration policy by itself.
    Who reads it and when. Only an operator uses it for an approved migration when the normal deployment path needs a database-level change. Runtime agents must not receive its credential.
    How to verify or reproduce it. First exercise the matching SQL against a disposable schema, confirm unauthorized and malformed requests fail, inspect transaction behavior, and compare the reviewed mirror with this source before live use.
    Related concepts. See change control, schema evolution, and the review mirror.
