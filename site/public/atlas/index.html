    The repo atlas

    TLDR

    The Repo Atlas is a guided map from repository paths to purpose. Every individually mapped tracked path has a detailed entry; named exclusion classes cover the remaining tracked paths. Search an exact path to reach its entry, or choose a repository area below. Each entry explains what the file is, what it contains, who uses it, how to verify it, and which concept page gives the larger meaning.

    What this page covers

    A repository is a versioned project folder. A path is the address of a file inside it, such as scripts/waking/orient.mjs. If those terms are new, start with Repository 101. The Atlas answers the next question: why does this particular file exist, and how does it fit the system?

    Concept pages explain organs and decisions. Atlas pages explain files. The two link to each other so a plain-language reader can move from an idea to its implementation, while an engineer can move from code back to its governing rule. An Atlas entry is not permission to run a file. Status still matters: a path may be active, built dark, generated, a fixture, a runbook, an archive, or governed material described without disclosure.

    Three ways to find a file

    1. Search the exact path. Open Search and paste the repository path. Exact path matches rank first and land on the immutable file heading.
    2. Browse by area. Use the grouped map below. Folders with many responsibilities have separate pages for lifecycle, signals, operations, tests, and verification.
    3. Follow a concept link. File lists on system pages link directly to the owning Atlas entry.

    How to read one entry

    Every tracked-file entry has the same five questions: what it is; what it contains; who reads it and when; how to verify or reproduce it; and which concepts explain the wider system. The badge names the file's role. Depth names explanation length, not importance: compact entries suit fixtures and generated data, standard entries cover active support code, and deep entries carry central mechanisms or authority.

    What complete coverage means

    The coverage map assigns individually mapped tracked paths by exact match or longest folder prefix. The generated manifest records the file anchors actually present. Verification compares both with the live tracked-file list, so additions, moves, wrong-page anchors, and orphaned entries surface. Named exclusion classes cover the remaining tracked public-site pages and selected generated outputs, avoiding circular self-documentation; the site page explains those classes. Ignored and local material has governed shapes rather than tracked anchors on the gitignored tiers page.

    Choose a part of the repository

    Design, identity, and family foundations

    • Root documents: design authority, build procedure, ledgers, decisions, licensing, secrets policy, and starting instructions.
    • Genesis avatar and Alpha avatar: manifests, per-being scaffolds, handoff shapes, and separation.
    • Brain definitions: fleet registry, canonical schema, migrations, and restore-point map.
    • Checklists, conventions, and handoff: executable procedure, cross-cutting rules, and session continuity.

    Research, records, and reusable material

    • Research and sources: evidence and source records that informed the design.
    • Runs: adversarial reviews, co-evolution bundles, and preserved build evidence.
    • Templates: schemas, contracts, runbooks, and disabled defaults used to reproduce operations.
    • Village material: human-facing bridge documents and governed family context.

    Runtime and operational code

    • Ingestion: fetching, parsing, filtering, and governed memory insertion.
    • Lifecycle and signals and evolution: waking, night work, study, weekly rebuilding, measurements, and proposal machinery.
    • Operations and task definitions: budgets, degraded mode, channels, recovery, security, and disabled schedules.
    • Brain lab scripts and edge functions: scratch brains, schema tooling, remote memory doors, and recall walls.
    • Voice core: prompt assembly, model backend, and mind-server seam.

    Tests, tools, and the website

    • Fixtures and test mode: synthetic days, Testweaver harnesses, and explicit cleanup.
    • Verify suite: the fixed ropes that turn assumptions into named checks.
    • Operator tools: the protected-shape probe runner.
    • This website: authoring contract, deterministic builder, search, gate, deployment metadata, and exclusion classes.
    • Gitignored tiers: secrets, runtime state, corpus bytes, telemetry, dependencies, and local tool state described without exposure.

    Full, lite, and gated views

    The gated site and full single-file edition carry every detailed entry. The lite edition removes the twenty-five detail pages but keeps one searchable line for every individually mapped tracked path on this hub; named exclusion classes cover the remaining tracked paths. Each line uses a distinct map identifier so it never pretends the missing detail is present. A lite search result says that detail lives in the gated or full edition. All editions come from the same authored main content and deterministic builder.
