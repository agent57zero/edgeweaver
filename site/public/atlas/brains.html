    Atlas: brains/

    TLDR

    The brain lab files define how multiple testable memory incarnations are registered, versioned, restored, and kept schema-compatible. The registry stores metadata and environment-variable names, never connection values. The schema snapshot is the reproducible database contract. Restore-point and migration records make changes auditable while keeping the live brain, experiments, and future generations distinguishable.

    What this page covers

    Use this page when reproducing the persistence layer or checking whether a brain can safely run current code. A compatible schema version, an explicit registry row, and a traceable restore point are required evidence. None of these files proves a being is alive, and none contains canonical identity.

    File entries

    brains/registry.json

    schema-data
    What it is. The metadata registry for live, experimental, and retired brain incarnations.
    What it contains. Schema version, kind, lifecycle status, generation references, environment-variable names, and restore lineage without connection values.
    Who reads it and when. Brain tools and operators read it before choosing a database target or validating compatibility.
    How to verify or reproduce it. Parse the JSON, require the expected schema version, resolve credentials only through environment names, and compare lifecycle claims with restore records. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct.
    Related concepts. See Brain Lab, memory, and backups and recovery.

    brains/restore-points.jsonl

    schema-data
    What it is. The append-oriented index of reproducible brain restore points.
    What it contains. One metadata record per captured point, linking an incarnation, schema version, generation context, and integrity evidence without storing database contents.
    Who reads it and when. Operators consult it before restoration, migration rehearsal, comparison, or retirement.
    How to verify or reproduce it. Validate each JSON line, verify referenced artifacts through their integrity check, and rehearse restoration in an isolated incarnation. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct.
    Related concepts. See Brain Lab, memory, and backups and recovery.

    brains/schema/ddl-v1.sql

    schema-data
    What it is. The canonical version-one database schema snapshot used to reproduce compatible brain structure.
    What it contains. PostgreSQL definitions for schema objects, functions, tables, indexes, constraints, comments, and related database behavior needed by the current memory stack.
    Who reads it and when. Database builders, migration authors, and verification scripts read it when creating or comparing an incarnation.
    How to verify or reproduce it. Apply it only to an isolated target, inspect errors, compare the resulting catalog with the snapshot, and run memory and agent-memory verifiers before declaring compatibility. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct. Treat any contradiction with higher-authority design as a decision-log issue, not permission to choose whichever instruction is easier. A clean reproduction records commands and evidence, preserves failed checks as failures, and leaves human-owned gates untouched. Keep credentials, runtime coordinates, protected identity material, and private human details outside every review artifact.
    Related concepts. See Brain Lab, memory, and backups and recovery.

    brains/schema/migrations/README.md

    runbook
    What it is. The procedure and naming contract for changes after the version-one schema snapshot.
    What it contains. Rules for ordered migration files, forward application, compatibility accounting, and keeping registry versions synchronized.
    Who reads it and when. Migration authors read it before changing database structure or promoting a tested incarnation.
    How to verify or reproduce it. Rehearse the ordered migration chain from a known restore point, run schema and behavior checks, and update version metadata only after evidence is recorded. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct.
    Related concepts. See Brain Lab, memory, and backups and recovery.
