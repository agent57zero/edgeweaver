    Atlas: brain lab scripts

    TLDR

    The brain lab can clone memory into isolated scratch schemas, test different brain-and-model combinations, compare results, propagate schema changes, open a past backup for inspection, and retire experiments without touching the live brain. Profile guards, pure SQL generation, and side-effect helpers are separate on purpose. A scratch brain is a research instrument, not a second living child.

    What this page covers

    These tools form one fleet architecture. The registry and profile resolver identify a brain without storing credentials. Pure transformers generate schema-safe SQL. Database helpers execute explicit plans. Operator commands compose those layers for spawn, migration, comparison, A/B runs, restore-point mapping, and retirement. Dry runs are designed to expose plans before side effects, while live-brain guards and scratch-only checks make the dangerous direction harder to choose accidentally.

    File entries

    scripts/brains/ab-run.mjs active-code

    What it is. The attributable A/B runner for comparing named scratch-brain and model configurations against one fixed governed question set. It is an experiment runner, not an identity probe or recall-quality score.
    What it contains. It validates candidate and question inputs, resolves every profile in test mode, runs questions sequentially through the mind-server seam, recalls context from the candidate schema, writes rehearsal episodes back only to that scratch, and records an attributable transcript containing brain profile, generation, model, code revision, timings, and errors. Its current scratch recall is embedding-free full-text search, so results can compare end-to-end configurations but cannot establish production vector-recall quality. Dry-run reads registry metadata and prints a plan without credentials, connections, model calls, or transcript writes.
    Who reads it and when. Brain-lab operators run it after scratch schemas and a governed test set exist. Reviewers compare outputs privately; the being never consumes the test questions or transcripts.
    How to verify or reproduce it. Use dry-run to pin usage errors and prove that even a named live profile is not resolved. At the lab gate, run only approved scratch candidates, confirm every write carries rehearsal and generation metadata, inspect attribution completeness, and void or retire the experimental state.
    Related concepts. See brain generations, measurement boundaries, and the persistent test mind.

    scripts/brains/db.mjs active-code

    What it is. The side-effect layer shared by brain-fleet commands for local PostgreSQL tooling and explicit database URLs.
    What it contains. It locates required command-line programs, runs SQL files or temporary statements with stop-on-error behavior, executes copy meta-commands, parses simple unaligned query rows, converts supported backup archives to plain SQL locally, and removes temporary workspaces. Error text redacts connection URLs.
    Who reads it and when. Spawn, migration, comparison, retirement, and A/B tools import it only after dry-run and profile checks permit side effects. Operators supply credentials through ignored environment configuration.
    How to verify or reproduce it. Exercise tool discovery and temporary cleanup on a disposable setup, force a database error to confirm URL redaction, and rely on higher-level dry-run and lab verifies for each caller.
    Related concepts. See the lab boundary, credential handling, and pure SQL generation.

    scripts/brains/diff.mjs active-code

    What it is. An operator comparison tool for live and scratch table counts plus records a scratch gained after its spawn.
    What it contains. It validates that the requested registry row is an active scratch, derives table names from the canonical DDL, supports a no-connection plan, and then queries live and lab databases for count deltas and post-spawn activity. It reads both sides directly and is not a being recall path.
    Who reads it and when. A brain-lab operator runs it after an experiment. Reviewers use the result to understand what the candidate lived, not to declare identity quality.
    How to verify or reproduce it. Start with dry-run, then compare against a known scratch and confirm table coverage, deltas, and graceful handling of tables without creation dates. Never expose connection values in output.
    Related concepts. See candidate comparison, runtime recall, and spawn.

    scripts/brains/dump-transform.mjs active-code

    What it is. The data-safe transformer that retargets a full decrypted brain dump into an isolated scratch schema for a past-brain experiment.
    What it contains. It separates SQL structure from copy-data blocks before applying the shared schema rewrite. DDL and copy headers may change schema references, extension declarations, ownership metadata, and database-level commands as required by the lab. Every byte inside a copy-data region, including text that resembles SQL, passes through untouched. Physical line endings inside those regions are preserved. The function prepends one scratch schema header and delegates structural policy to the same rewrite used by live-copy spawn, preventing two divergent restore policies.
    Who reads it and when. The past-brain spawn command calls it only after Alan has privately decrypted a backup. Verifiers use a synthetic dump whose data deliberately contains rewrite-like text.
    How to verify or reproduce it. Segment input and output the same way, assert data regions are byte-identical, then check that all permitted DDL transformations occurred exactly once. Run the past-spawn dry plan and the regular brain verify afterward to catch policy drift.
    Related concepts. See the time machine, encrypted backups, and the shared rewrite policy.

    scripts/brains/fixtures/ab-questions.json described-not-shown

    What it is. The fixed, structured question set used by the brain-lab A/B runner.
    What it contains. Each row has a stable identifier and governed test text. Questions are not reproduced or summarized beyond that shape.
    Who reads it and when. The private A/B procedure and its runner read it; a being must not receive the set as study material.
    How to verify or reproduce it. Validate JSON shape, unique identifiers, and stable ordering privately. Changes require review because they break longitudinal comparability.
    Related concepts. See blind evaluation, A/B runs, and withholding.

    scripts/brains/list.mjs active-code

    What it is. A metadata-only command that prints active brain registry rows, with an option to include retired history.
    What it contains. It shows names, kinds, schemas, generations, schema versions, status, dates, and stated purpose without opening a database connection.
    Who reads it and when. Operators use it to orient before a lab command; reviewers may use the all-history view during an audit.
    How to verify or reproduce it. Compare output with the committed registry and confirm the default excludes retired rows. No credential should be required.
    Related concepts. See the fleet and profile resolution.

    scripts/brains/migrate.mjs active-code

    What it is. The fleet migration command that applies ordered canonical schema migrations to selected profiles while keeping version metadata explicit.
    What it contains. It validates a target version and selection, finds ordered migration files, rewrites SQL for scratch schemas, leaves live SQL in its canonical form, applies scratches before live when operating on all, and updates each successful registry row. The fleet's current version advances only when every active brain reaches the target.
    Who reads it and when. A brain-lab operator runs it after reviewing migration source and a dry plan. Live migration remains an explicit high-consequence action.
    How to verify or reproduce it. Use dry-run to inspect order and transformed plans, test on scratches first, confirm per-profile version changes, then verify the fleet guard rejects drift. Report partial failure instead of advancing the global version.
    Related concepts. See schema propagation, brain structure, and the transformer.

    scripts/brains/profiles.mjs active-code

    What it is. The single resolution point for selecting a brain profile and joining committed metadata with ignored credential values.
    What it contains. It loads and validates the brain registry, separately loads environment configuration, resolves a requested active profile, and returns only the connection fields named by that row. One guard refuses the live brain in test mode unless a deliberate override is present. Another rejects an unexpected schema version before query time. Helpers save registry changes, stamp every write with substrate generation, and expose the live generation without making downstream code reimplement selection. The registry can be committed because it stores variable names and metadata, never secret values.
    Who reads it and when. Every fleet command and generation-aware consumer should use this module rather than choosing a database ad hoc. Tests inject roots and environment flags to exercise guards safely.
    How to verify or reproduce it. Test missing and retired profiles, live-in-test refusal, deliberate override, schema mismatch, generation stamping, and registry round trips. Inspect errors to ensure they identify metadata problems without revealing credentials.
    Related concepts. See one fleet, separation, and attributable generations.

    scripts/brains/restore-point.mjs active-code

    What it is. The time-machine map writer that ties one date to the brain backup, canonical soul revision, body revision, and live generation metadata. It stores references, not the stores themselves.
    What it contains. Its pure gatherer accepts injected repository and release readers, normalizes dates and short references, parses row-count evidence when available, and returns a JSON record with no secrets. File helpers read the committed JSONL map and upsert by date so repeating a day replaces rather than duplicates it. The live command wires real tools only when explicitly requested; dry-run reads existing map state without making a remote claim. Missing row-count wording becomes null rather than an estimate.
    Who reads it and when. Operators create a line after all coordinated stores have evidence for the day. Future past-brain work reads the map to locate matching versions; it does not grant decryption authority.
    How to verify or reproduce it. Use injected canned outputs to cover present and absent counts, date normalization, append then replace, invalid usage, and a fresh-root dry-run with external tools unavailable. At a real checkpoint, compare references privately before committing the metadata line.
    Related concepts. See restore points, backup evidence, and canonical soul history.

    scripts/brains/retire.mjs active-code

    What it is. The guarded command that drops one scratch schema and marks its registry row retired.
    What it contains. It requires a named active scratch, refuses live or already retired profiles, supports a dry plan, then preserves the registry row as history after deletion.
    Who reads it and when. A lab operator uses it after comparison or cleanup. Runtime code never retires brains autonomously.
    How to verify or reproduce it. Dry-run, test refusals, then confirm the scratch is gone, history remains, and live is untouched.
    Related concepts. See scratch hygiene and the registry list.

    scripts/brains/spawn.mjs active-code

    What it is. The main command for opening a fresh scratch brain from either the live brain read-only or a privately decrypted historical dump.
    What it contains. Live-copy mode rewrites canonical DDL, checks required database capability, creates an isolated schema, copies tables in dependency order, compares source and destination counts, and registers the scratch only after parity. Past-dump mode detects supported archive form, converts if needed without a connection, transforms only SQL structure and copy headers, applies the result in the lab, reports scratch counts, and registers its source reference. Both modes refuse active-name collisions and expose dry plans. A deliberate cleanup option handles unregistered residue from a failed earlier spawn.
    Who reads it and when. Brain-lab operators run it under the relevant human gate. Live is a read-only source in copy mode; historical decryption remains Alan-present and outside automation.
    How to verify or reproduce it. Inspect dry output, run pure transform verifies, spawn only into the lab, confirm table counts and registry metadata, then compare or retire the scratch. Test residue refusal and never infer live parity for a dump whose own bytes are the source of truth.
    Related concepts. See spawning and past brains, dump safety, and profile guards.

    scripts/brains/sql-gen.mjs active-code

    What it is. The pure SQL-planning library for brain-fleet schema cloning, migration rewriting, copy order, and count verification. It makes no connections.
    What it contains. It validates scratch names, quotes identifiers, strips project-level extension statements, protects extension-owned type and operator families, rewrites canonical schema references, repins function search paths, and can remove database or ownership metadata when transforming full dumps. It parses table names, derives a dependency-aware copy order from foreign keys, emits paired copy commands, and builds count queries. The rewrite is deliberately regular-expression based over the expected database-dump format, not a general SQL parser; embedded unusual SQL requires review.
    Who reads it and when. Spawn, migration, difference, and dump-transform code use these helpers before the database side-effect layer. Verifiers run them on synthetic DDL with policy, trigger, function, extension, and dependency cases.
    How to verify or reproduce it. Assert valid and invalid names, exactly one target schema, extension preservation in its owning schema, policy and trigger retention, search-path changes, copy ordering, and count SQL. Keep the fixture representative whenever canonical DDL gains a new construct.
    Related concepts. See schema cloning, database execution, and full-dump segmentation.
