    Atlas: site/ (this website)

    TLDR

    This website is hand-authored static HTML with deterministic generation around it. Authors own each page's main content; shared partials, metadata, and the builder produce navigation, local search, continuation cards, Atlas coverage, and two single-file editions. The deployment adds a courtesy password gate, but safety comes from publishing no secrets or protected material. Generated outputs are committed evidence, never the source of truth.

    What this page covers

    The entries distinguish authored contract and configuration from executable build code and generated search data. They also explain which tracked website paths deliberately do not receive individual Atlas anchors. That exception keeps this self-documenting site from creating dozens of circular entries while still giving every excluded class a named home, a verification rule, and a searchable explanation.

    File entries

    scripts/site/build-site.mjs active-code

    What it is. The deterministic assembler for shared page chrome, local search, Atlas manifest, and the full and lite single-file editions. It is the only writer for marked generated regions and outputs.
    What it contains. It validates navigation hubs, page metadata, audiences, and reading tracks; fills head, contextual navigation, breadcrumbs, search dialog, local find fallback, page tables of contents, continuation cards, and footer markers; extracts authored main content into normalized search records; scrapes file anchors into the manifest; and builds self-contained artifact documents with one main landmark and page articles. The generated search index and artifacts share those builder in-memory records; artifacts do not read generated JavaScript. Lite output omits detailed Atlas pages while adding one distinct map row for every individually mapped tracked path; named exclusion classes cover the remaining tracked paths. Exact path mappings override broad exclusion classes. Check mode computes all outputs in memory and reports stale files without writing.
    Who reads it and when. Luna runs it under a writer freeze after authors stop. Authors edit only main content and shared owners edit partials or metadata; end users consume its outputs.
    How to verify or reproduce it. Run check mode for freshness, regenerate once under freeze, rerun check, compare byte identity, and execute default, live-drift, redaction, and release verification as required. Never resolve coverage from Git inside the builder itself.
    Related concepts. See how the site is made, Repository 101, and the authoring contract.

    site/.gitignore schema-data

    What it is. The site-local ignore rules for deployment-tool state and environment files.
    What it contains. It excludes the local project-link directory and every site-level environment file, preventing machine metadata and passwords from becoming tracked website source.
    Who reads it and when. Git applies it during local deployment work; operators review it before adding configuration.
    How to verify or reproduce it. Use Git's ignore explanation on representative local files and confirm no ignored value appears in tracked status or Atlas output.
    Related concepts. See secret separation and ignored tiers.

    site/.vercelignore schema-data

    What it is. The deployment-upload exclusion list for material that Vercel does not need to serve.
    What it contains. It omits authoring sources, artifact editions, the handoff README, and repository-only metadata from uploads. Public output and gate code remain deployable.
    Who reads it and when. The deployment client reads it during a manual site release; maintainers review changes with the build layout.
    How to verify or reproduce it. Inspect the upload plan privately; smoke-test a page, asset, nested Atlas route, and missing route through the gate.
    Related concepts. See editions and manual release.

    site/README.md runbook

    What it is. The maintenance guide that becomes the explainer site's operational handoff only after Luna updates it.
    What it contains. After Luna updates it, it records the current execution resume point, build and verification commands, preview options, source and generated layout, password-gate handling, editorial rules, and milestone ledger. It is a status aid for builders, not the public conceptual guide or design authority.
    Who reads it and when. The next coding agent reads it as the handoff after Luna's update; until then, its resume and milestone prose is not current handoff status. A newcomer should use the Reading Guide for repository vocabulary.
    How to verify or reproduce it. After Luna updates it, reconcile its commands, generated-output list, active phase, and milestone state with the plan and actual scripts. Remove stale claims rather than treating prose as automatic status.
    Related concepts. See How to read this site, project status, and authoring rules.

    site/middleware.js active-code

    What it is. The framework-less routing middleware that places every deployed path behind one shared password gate. It is explicitly a courtesy and team-grade privacy wall, not a vault.
    What it contains. It reads the password only from the deployment environment, fails closed when absent, derives a deterministic HMAC bearer cookie, compares values without early exit, parses cookies, sanitizes local return paths, serves its own no-store login form, delays failed attempts, and lets authenticated requests continue to static files. No route matcher or public login carve-out exists, so pages, assets, Atlas routes, and missing paths all cross the same middleware. Rotation changes the derived cookie and ends old sessions. Current pre-release code does not yet claim the later logout, minimum-length, or full security-header hardening.
    Who reads it and when. Every deployed request passes through it. Alan controls the environment value and rotation; site authors never handle the password.
    How to verify or reproduce it. With a throwaway development value entered only through the browser, test missing configuration, wrong password, successful cookie flow, nested pages, assets, login return, and rotation. Before release, complete the separate gate-hardening checklist and inspect response headers without publishing the host.
    Related concepts. See the courtesy-wall limit, secret boundaries, and release operations.

    site/package.json schema-data

    What it is. The minimal Node package marker for the framework-less static site.
    What it contains. It names a private package and selects module semantics. No dependencies or scripts exist; commands live in the site README.
    Who reads it and when. Node and the deployment platform use it to interpret JavaScript modules. Maintainers read it when adding tooling.
    How to verify or reproduce it. Parse it as JSON, confirm private status and module mode, and avoid inventing an install or test step that the manifest does not define.
    Related concepts. See the dependency-free site and build commands.

    site/public/assets/search-index.js generated

    What it is. The generated, network-free search dataset for every web page.
    What it contains. It carries a release identifier and normalized heading and file records: destination, audience, register, badges, path, and text. It stores no queries or analytics.
    Who reads it and when. Browser search loads it. Artifacts receive the builder's shared in-memory records instead; they do not read this generated JavaScript. Authors never edit it.
    How to verify or reproduce it. Rebuild under freeze; parse the payload, check destinations and redaction, and test exact-path ranking.
    Related concepts. See local search, generated outputs, and the builder.

    site/src/AUTHORING.md authority

    What it is. The binding editorial and markup contract for every authored byte in the explainer. The higher design plan governs it when a conflict is discovered.
    What it contains. It defines secret, probe, identity, people, status, canonical-soul, and operational redaction rules; page mechanics and relative links; navigation metadata; deterministic search; progressive enhancement and reading lens behavior; exact Atlas article fields, badges, and depth bands; accessibility requirements for controls, tables, diagrams, anchors, mobile, print, and reduced motion; diagram conventions; and the allowed targeted self-check. It also separates machine-owned marker regions from author-owned main content and forbids authors from racing the builder.
    Who reads it and when. Every site author and reviewer reads it fully before editing. Luna owns shared implementation, while Atlas authors follow its frozen entry contract inside assigned pages.
    How to verify or reproduce it. The release verifier automates structural portions, but editorial review must still inspect truth, redaction, plain-language quality, and authority conflicts. Update the contract and verifier together when a rule becomes mechanical, then regenerate only under the integration freeze.
    Related concepts. See editorial honesty, authority order, and site method.

    site/src/allowed-domains.txt schema-data

    What it is. The small editorial allowlist for external hyperlinks in site pages.
    What it contains. It lists approved host domains only, one per line. It is not a network firewall, runtime service list, or permission to load remote assets.
    Who reads it and when. The site verifier reads it; authors consult it before adding a rare external citation.
    How to verify or reproduce it. Confirm every external anchor is secure and on the list, every remote asset or fetch remains forbidden, and each domain is still necessary.
    Related concepts. See attribution and network boundaries.

    site/src/atlas-map.json schema-data

    What it is. The coverage-routing table that assigns every individually mapped repository path to one Atlas page and names exclusion classes for the remaining tracked paths.
    What it contains. It defines exact paths and longest-prefix destinations plus named exclusions for the broad site-page surface and selected generated outputs. The lite map has one row for every individually mapped path, while these named exclusions cover the remaining tracked paths. An exact mapped file, such as the generated search index, overrides a broad excluded prefix. Notes record the page responsible for explaining each exception.
    Who reads it and when. The builder uses it when emitting the committed manifest; live-drift verification compares its policy with tracked files. Atlas authors use it to respect ownership, never to derive content.
    How to verify or reproduce it. Run the read-only tracked-path comparison after additions or renames. Require zero unmapped paths, no wrong-page anchors, no orphaned manifest entries, and a documented home for every exclusion.
    Related concepts. See the Repo Atlas, tracked paths, and this coverage rule.

    site/src/nav.json schema-data

    What it is. The single metadata source for page order, five hubs, reading tracks, titles, snapshot, release identifier, search classification, and audiences.
    What it contains. Every page record supplies slug, title, milestone, hub, subsection, kind, summary, and one or more approved audiences. Hub definitions name their landing pages, while three explicit tracks define continuation cards without inferred state.
    Who reads it and when. The builder validates and renders it into shared navigation, breadcrumbs, search records, artifact contents, and continuation links. Authors consult it but do not change slugs casually.
    How to verify or reproduce it. Require exactly five valid hubs, unique slugs, known kinds and audiences, complete metadata, nonrepeating valid tracks, and a deliberate release identifier before shipping. Then test every generated destination.
    Related concepts. See reading paths, site structure, and the renderer.

    site/src/partials/footer.html active-code

    What it is. The shared closing template inserted after every authored main.
    What it contains. It holds generated continuation-card placement, the village-layer banner, documentation license and attribution, snapshot, and release identifier.
    Who reads it and when. The builder reads it for web pages; authors see its output but do not edit marker regions.
    How to verify or reproduce it. Regenerate and confirm every page has one footer, correct local links, current release metadata, and required attribution in both artifacts.
    Related concepts. See license and editions and the builder.

    site/src/partials/head.html active-code

    What it is. The shared document-head template for every static page.
    What it contains. It declares encoding, viewport, no-index metadata, release metadata, a page title, local stylesheet, generated search data, and enhancement script using the page's relative root.
    Who reads it and when. The builder inserts it; browsers load the resulting local resources.
    How to verify or reproduce it. Check every page has one resolved title and root-correct local asset paths under file, static HTTP, nested Atlas, and gated modes.
    Related concepts. See network-free design and local search.

    site/src/partials/nav.html active-code

    What it is. The shared shell for controls, search, contextual navigation, breadcrumbs, reading column, and on-page rail.
    What it contains. It provides accessible labels and placeholders for hub links, mobile controls, search, reading detail, theme, snapshot, no-JS help, TOCs, and the page main boundary.
    Who reads it and when. The builder fills it for every page; browser JavaScript progressively enhances its controls.
    How to verify or reproduce it. Regenerate and keyboard-test search, lens, drawer, skip link, breadcrumbs, TOCs, focus return, no-JS, nested roots, and print.
    Related concepts. See site controls, accessibility, and navigation metadata.

    site/vercel.json schema-data

    What it is. The static deployment configuration for the gated site project.
    What it contains. It names the public output directory and applies a robots exclusion header across routes. Password behavior remains in middleware, not this file.
    Who reads it and when. The deployment platform reads it during a manual release; operators review it with gate and cache policy.
    How to verify or reproduce it. Validate configuration, inspect response headers on representative gated routes, and confirm only public output is served. Complete release hardening before deployment.
    Related concepts. See manual deployment, privacy limits, and the gate.

    Tracked exclusion classes

    site/public/: site-pages

    The authored HTML pages, shared stylesheet, and browser enhancement script are tracked and served, but they do not each receive a circular file entry. Their concepts are the site itself; their shared authoring, build, search, and verification rules are documented on this page. The exact-mapped generated search index is the deliberate exception and has its own entry above.

    Generated editions and manifest

    The committed full artifact, lite artifact, and Atlas manifest are deterministic builder outputs. They carry no individual file-* anchors because editing them directly would reverse source and output. The builder entry explains reproduction; freshness and release verification prove that each generated byte matches authored pages, metadata, partials, and styles.
